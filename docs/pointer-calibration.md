# 指针标定：CNC 式四角归零（换设备自动适配）

> 结论先说：这块板子的鼠标**精度已经到单像素级**（闭环落点平均 1 px、最差 1 px），
> 用「撞屏幕四边 = 撞硬限位」的四角归零法，可以在**任何分辨率/缩放的设备上自动量出**
> 屏幕尺寸与位移增益，换设备不需要改代码。2026-10-18 在本机（2560×1440 @125%）
> 实机跑通，耗时 7.7 s。

## 0. 为什么屏幕四边等于限位开关

板子是**相对** HID 鼠标：只能发「走多少个 count」，没有 `SetCursorPos` 权限。
但 Windows 会把光标裁在虚拟桌面边界上——所以「拼命往左上推」最后一定精确停在
`(0,0)`。这和 CNC 撞硬限位回零是同一个道理：**绝对参考点由物理（这里是系统）
边界给出，而不是由编码器给出。**

## 1. 流程（`tools/home-calibrate.py`）

```
[1] 四角撞边：左上 → 右上 → 右下 → 左下，每轮推 1500 counts，两轮位置不变即到边
[2] 量量具  ：四角坐标直接给出虚拟桌面 原点(0,0) 尺寸 2560x1440，与 GetSystemMetrics 对比
[3] 重标增益：屏幕中心重测 count→px 增益（加速曲线）；小位移连发 10 次取平均消量化噪声
[4] 验收    ：四角内缩 24 px 处 + 屏幕中心，闭环 locate(tol=1) 落点误差
[5] 存档    ：profile 按「分辨率+虚拟桌面+DPI 模式」做 key 写入 pointer-profile.json
[6] 收工    ：光标放回标定前位置；全程不点击、不按键
```

用法（走 hub 8766 透传，**不用停网页**）：

```bash
python tools/home-calibrate.py --transport tcp --apply
```

## 2. 本机实测（2026-10-18 00:53，2560×1440 @125%，per-monitor-aware）

四角撞边（每角 2 轮到位）：

| 角 | 停点 | 期望 |
|---|---|---|
| 左上 TL | (0, 0) | (0, 0) |
| 右上 TR | (2559, 0) | (2559, 0) |
| 右下 BR | (2559, 1439) | (2559, 1439) |
| 左下 BL | (0, 1439) | (0, 1439) |

→ 量出虚拟桌面 **2560×1440 @ (0,0)**，与 `GetSystemMetrics` 一致（DPI 缩放被正确还原为物理像素）。

增益重测（px/count，屏幕中心量）：

| 发 m count | 1 | 2 | 3 | 4 | 6 | 8 | 12 | 16 | 24 | 40 | 60 | 120 | 200 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 增益 | 0.70 | 0.75 | 0.83 | 0.90 | 1.12 | 1.25 | 1.29 | 1.50 | 1.85 | 1.98 | 2.23 | 2.23 | 2.60 |

这张表就是 Windows「提高指针精确度」的加速曲线：**小位移 1 count 还不到 1 px，大位移被放大 2.6 倍**。
所以「开环直推」大范围移动必然偏，必须闭环。

落点验收（tol=1）：

| 目标 | 实际 | 误差 | 迭代 |
|---|---|---|---|
| (24, 24) 左上内缩 | (23, 24) | 1 px | 4 |
| (2535, 24) 右上内缩 | (2535, 24) | 0 px | 7 |
| (2535, 1415) 右下内缩 | (2535, 1415) | 0 px | 3 |
| (24, 1415) 左下内缩 | (24, 1415) | 0 px | 7 |
| (1279, 719) 屏幕中心 | (1279, 718) | 1 px | 5 |

**最差 1 px，5/5 命中 ≤1 px。**

另外用档案（profile 增益表）自动生效后复测 3 个点：0 / 1 / 1 px，光标已放回原位。

证据：`docs/evidence/home-calib-20261018-005311.txt`（成功那次）、
`docs/evidence/home-calib-20261018-005242.txt`（首次：在角落量竖向增益被边界裁掉，量出 0，
说明「必须在屏幕中间量」——保留作为反例）。

## 3. 换设备怎么「自己适配」

签名 = `2560x1440|virtual=2560x1440|dpi=per-monitor-aware`。换到 1080p 设备后：

1. 任何用 `pc/brain.py` 的动作，`Brain.__init__` 会查 `C:\ProgramData\dsh\pointer-profile.json`；
2. 签名对不上 → 不做隐式标定（绝不偷偷抢鼠标），而是 `pc/pointer_profile.py ensure()`
   打印提示：跑一次 `python tools/home-calibrate.py --transport tcp --apply`；
3. 跑完后该设备的增益表进档案，同一签名下次启动**自动生效**（`Brain.gain_source = profile:<签名>`）；
4. 旧设备的档案不会被覆盖（JSON 里按签名分 key，多台设备共存）。

CLI 查看：

```bash
python pc/pointer_profile.py status
```

## 4. 精度上限与「真·高精度」路线

| 路线 | 精度 | 状态 |
|---|---|---|
| 相对 HID + 闭环落点 | **≈1 px**（实测） | ✅ 已实现，`brain.locate(tol=1)` |
| 四角归零 + 设备档案 | 同上，且换设备免改代码 | ✅ 已实现（本文） |
| **绝对坐标 HID**（固件改描述符：Usage 0x30/0x31，logical 0..32767） | 像素级、误差≈0，免疫加速曲线，换分辨率天然适配 | ⬜ 待做：改固件 + 重烧 + 验证 Windows 识别（可能被当「笔/数字化仪」） |
| 数字化仪/笔（HID Usage 0x0D + Pressure） | 绝对坐标 + 压感（画画能吃压感） | ⬜ 待做，同上 |

绝对坐标的价值：它是「直接告诉系统我在屏幕的百分之几」，不是「走多少步」——
标定这一步都可以省掉。但会改变 Windows 侧的设备类型识别，需要实机验证兼容性。

## 5. 已知边界（诚实说明）

- **多显示器**：撞边撞到的是**整个虚拟桌面**的边界，不是主屏边界；多屏时四角给出的是
  虚拟桌面外框（原点可能是负数），目标屏内的定位仍靠闭环 `locate()`（坐标已知，没问题）。
- **指针加速**：不改进你的系统设置（不改注册表）；闭环 + 1:1 精修区已经把影响吃掉。
- **用户抢鼠标**：`locate()` 有 `PointerGuard` 判用户介入，介入就把真实位置当新锚点，不硬拽。
- **测增益必须在屏幕中间**：在角落某方向被裁，会量出 0（见反例证据）。
- **125% 缩放**：进程必须先开 DPI 感知（`eyes.enable_dpi_awareness()`），否则拿到的是逻辑像素
  （2048×1152），与 `GetCursorPos` 不在一个坐标系。
